# .docx export clones pieces from the Resume Template's Word XML, not a fixed layout or from-scratch generation

The exported resume needed to match `backend/templates/resume_template.docx`'s actual visual design (fonts, colors, spacing, a colored header banner, a rule under each section title) — a real, user-facing artifact, not throwaway output. Filling the template directly was rejected: its body is a fixed layout (a fixed number of jobs, fixed section order), and a Profile's variable-length, reorderable sections don't fit it. Generating from scratch (`Document()`, hand-picked `Pt()`/`RGBColor()` calls) was tried first and rejected too — the output didn't resemble the template at all: no header banner, the wrong heading size, dates crammed inline instead of on their own line, default margins instead of the template's. Every value was a guess at what the template intended, and several were wrong. The export instead deep-copies representative pieces (a section heading, job title line, dates line, bullet, tags line, header banner) directly out of the template's Word XML, refills them with the Profile's content, and reassembles a new document — formatting stays byte-identical to the template without being re-derived by hand in Python, while still supporting a variable number of freely-ordered sections since only small pieces are reused, not the whole document structure.

This makes the Resume Template a live formatting source rather than passive reference material: editing its fonts/colors/spacing changes every future export automatically, and each cloned piece carries a native Word comment explaining what it's used for — open the file in Word and check the comment balloons before changing its layout. It also means the template's own leftover metadata can leak in ways invisible from reading a paragraph's own XML: nearly every paragraph carries a `w:divId` left by an HTML/web-paste origin, which links to a *separate*, fixed-color border definition in `word/webSettings.xml`; stripped at clone time, or it silently duplicates a border in every export. The same applies to the template's own Word comments: their in-body anchor markers and the `word/comments.xml` part itself are stripped per clone, or template-editor notes would ship inside every Candidate's downloaded resume. A picture frame's exact width/height lives in the template's own XML (`wp:extent`); an uploaded photo is center-cropped to that frame's aspect ratio in Python before embedding, and the frame's own size is left untouched, so it's always exactly the template's size regardless of what a Candidate uploads. An alternate header banner for Profiles with no photo lives on its own page within the same file, not a separate document, so both banners share one `styles.xml`/`docDefaults` and can't silently drift out of sync with each other.
